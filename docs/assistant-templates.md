# Assistant templates

RiA's shared instructions cover how it interprets the user's request, uses evidence and verifies delegated work. Simple questions can get a direct reply. Longer tasks can use planning, progress updates and checks appropriate to the work. The instructions call for checking earlier results before repeating actions that may already have taken effect. Workspace guidance applies to its active workspace, and retrieved material supplies evidence. Active tools provide their own usage instructions, and the application enforces permissions and approval rules.

The four default templates and their tools:

| Template | Revision | Focus | Tools |
|---|---|---|---|
| Knowledge assistant | 4 | Ground answers in the user's material, checking the surrounding passage when scope is unclear. | Knowledge search, read document, web search, convert and export document, save knowledge entry |
| Writing assistant | 3 | Write for the audience and purpose. Preserve meaning, voice and established facts when revising. | Knowledge search, read document, web search, convert and export document, save knowledge entry |
| Coding assistant | 5 | Trace the behavior to the code that owns it and choose checks that exercise the change. | Terminal and its companion tools, knowledge search, read document, web search, create task |
| Research assistant | 4 | Prefer original sources and compare claims in their date, scope and context. | Web search, knowledge search, read document, convert and export document, save knowledge entry, create task |

Every template can also read enabled plugin skills on demand and compact its context. Saving knowledge entries, creating tasks and external extension tools still require approval in the conversation. When a chat fallback model is configured, a conversation with tools is also taken over by the fallback model when the primary model is unavailable, with tools, template instructions and context unchanged (the fallback model must support tool calls). For five minutes after the primary model fails, later requests go to the fallback model first; see [Model usage](model-usage.md).

The upgrade revises built-in templates that still have their shipped instructions and revision. It preserves user edits and deleted defaults. New conversations use the current template. Existing conversations keep their saved template snapshot until the user chooses **Template details → Update to latest template**. Updating the template retains earlier messages.

Open **Assistant templates** from the sidebar. Templates are shown as a compact list. **New template**, or **Edit** in the more-actions menu, opens the editing dialog, centred over the page like the one for a new task and wider, for the instructions; closing it with changes not yet saved asks before discarding them; the retrieval strategy is collapsed by default. Default templates can be edited and deleted just like custom ones. **Create copy** in the more-actions menu opens a drawer prefilled with the configuration, which becomes an independent template when saved. After a default template has been deleted, the “Default templates” group shows **Restore defaults**, which puts back only the deleted default templates; those still present keep your changes. The **Copy assistant instructions** button writes the instructions straight to the clipboard and reports success or failure. Up to 50 custom templates can be stored (default templates excluded), and deletion asks for confirmation.

A template stores its name, description, assistant instructions, an optional chat model binding, the allowed tools, topics, the long-term memory switch and the retrieval strategy. Without a bound model it follows the conversation's model. A bound model must be among the chat models in **My models**; after that model is removed, the template must be corrected or detached from the conversation before calls can continue. Templates grant no folder permission and do not bypass tool approval, the model allow-list or run budgets.

**New conversation** copies the configuration into a persisted conversation snapshot, and the default title is the template name. A template can also be applied to an existing conversation from the menu on the conversation's title, in the window's top row; beside the title, the template's name shows while one is in use. When the current title is a placeholder or the old template's name, switching, updating or removing the template updates the default title; a conversation the user has named keeps its title, and a title explicitly submitted in the same request takes precedence. Applying a template sets the memory switch and clears the history compaction cache, and while it is applied its topics decide what the conversation searches; removing it leaves the conversation searching the whole library; the original messages are unchanged. An empty tool list disables tools, and the server validates both automatic tool use and explicit tool calls that carry a `chatId`. A conversation without a template is the **General assistant**: it can use every configured tool and has no template instructions, while still following each tool's approval requirements and folder permissions.

Editing or deleting a template does not change existing conversations. The chat page no longer shows the snapshot revision and tool count at all times; **Template details**, in the same menu, opens a drawer on the right with the snapshot revision, tool count and model used by the current conversation, the template's memory and knowledge scope, and its assistant instructions. The details are read from the configuration saved in the conversation, so they remain available after the original template is deleted. Closing the drawer returns focus to the conversation title, and the drawer uses the existing drawer animation and reduced-motion setting. When a newer revision exists, it is adopted only after **Update to latest template**; if the template fails to load, the action can be retried. A request that has already started uses the model, instructions, tools, topics and memory policy it obtained when it started; a new configuration applies from the next request. A conversation can override its topics or memory switch on its own; applying the template again resets them to the template's values. Removing a template keeps the current topics and memory switch and restores the default instructions and tool scope.

Templates have no retrieval settings of their own: every search uses the same defaults (at most 8 sources and 8000 characters of excerpts). A template or conversation saved when templates still carried a retrieval strategy reads without error, and that setting is ignored; saving the template again leaves it out.

## Local API

- `GET /api/assistants`: default and custom templates, with the fields `id`, `revision`, `builtin` (whether it is a default template) and `config`. Default templates come first.
- `POST /api/assistants`: submits a configuration and creates a custom template. The model is `{providerId, modelId}` or `null`; `tools` is required and may not contain duplicates; the other fields correspond to the configuration described above.
- `PATCH /api/assistants/:id`: `{revision, config}`. A revision mismatch returns 409 so that another edit is not overwritten.
- `DELETE /api/assistants/:id?confirm=true&revision=1`: no request body; confirms deletion of the given revision. This also applies to default templates.
- `POST /api/assistants/defaults`: puts back deleted default templates and returns `{data, restored}`; default templates that still exist are not rewritten.
- `POST /api/conversations`: may include `assistantTemplateId`. Creating the same conversation ID again does not overwrite its snapshot.
- `PATCH /api/conversations/:id`: `{assistantTemplateId}` applies the latest configuration, and `null` removes it. Do not mix a template change with topic or memory overrides in the same request.

Template writes are limited to 30 per minute, and every endpoint uses the existing local credential, Host/Origin checks and restore mutual-exclusion rules. Conversation lists and details return `assistantConfig`, which is `null` for older conversations. A conversation bound to a template model rejects a different model sent by the client.

The SQLite migration that added templates keeps existing conversations and data, and on the first upgrade the desktop migrator makes a safety copy of the database. Portable backups include every template (default templates included) and every conversation snapshot. Restoring maps the identities of custom templates, while default templates keep their original IDs. Snapshots of deleted templates are retained as well. After restoring an older backup without default templates, **Restore defaults** puts them back. A new backup must be restored by the same or a later version. Existing folder authorizations are still revoked on restore. No new environment variables or dependencies are required.

Acceptance covers editing, deleting and restoring default templates, copying a template, setting topics and tools, and creating a conversation; after editing a template, check that the old snapshot is unchanged, update it explicitly, then delete the template and restart the service to confirm that the conversation keeps its snapshot. Tool restrictions, restore and migration are covered by automated tests; the quality of real model answers is checked separately through the [knowledge search evaluation](document-knowledge.md).
